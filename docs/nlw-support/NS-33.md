# NS-33 — deleting annotations

Research and implementation plan only, 2026-10-22. Ticket: <https://digirati.atlassian.net/browse/NS-33>. Source paths below are relative to `services/madoc-ts`, except explicitly identified sibling-repository evidence. No source changes or runtime deletion were performed.

## Current state and verified fixes

The ticket combines bulk cleanup, task/contribution deletion, and removal of approved work. These are different operations in the current implementation.

* MAD-1293 was implemented: merge `630a0aa3` (PR #757, 2023-08-23) added deletion of user tasks to the old canvas bulk-delete control; `CHANGELOG.md` records it in v2.1.4. This establishes that the original missing-cleanup report was addressed, not that every current deletion path is correct.
* NS-76 subsequently moved canvas deletion into `src/routes/projects/delete-project-capture-model.ts`, introduced in `f419ecc5` (2025-08-05; v2.2.9). `src/frontend/site/features/canvas/CanvasTaskProgress.tsx` now calls `api.deleteProjectCaptureModel(projectId, modelId)`. The route requires `site.admin`, deletes the model, then deletes **contribution tasks** matching project root and Canvas target, provided `derivedFrom` matches the project template model. It uses `all:true, all_tasks:true` to avoid the normal task-page limit.
* Model deletion is site-scoped and cascades revision rows through the existing FK (`migrations/2022-08-25T15-23.capture-model-database.sql`). It does not itself delete external task records. The route checks the project/template relationship **after deleting the model**, catches all errors, and returns 204 even after failure. It does not explicitly remove review or structural tasks, reopen completed parents, reindex, or refresh task queries in the UI. These are remaining concerns, not grounds to reimplement MAD-1293 from scratch.
* NS-67 (`d145329d`, 2025-08-21) added a manifest “Delete all contributions” control in `src/frontend/site/features/manifest/ManifestTaskProgress.tsx`. It calls **only** `api.deleteTask(manifestTask.id)` and refetches task data. No capture-model deletion is in this call path. Its promise to delete all manifest/canvas contributions is therefore not established by Madoc code.
* `src/extensions/capture-models/crowdsourcing-api.ts::reviewRejectSubmission` retains the revision with status `rejected` and sets its contribution task to -1; `src/frontend/site/pages/tasks/actions/reject-submission.tsx` still says it deletes the revision. Rejection is not permanent deletion, and the control excludes approved revisions.
* Raw revision deletion exists (`crowdsourcing.deleteCaptureModelRevision`; `src/capture-model-server/routes/delete-revision.ts`, requires `models.create`). It removes a revision row only. `server-filters/filter-missing-revisions.ts` hides orphan revision-tagged values on reads; it does not physically remove all document values or synchronize tasks. Values already made canonical by direct edits/merges cannot be identified as exclusively owned by that deleted revision.

### External task deletion evidence and limitation

The read-only sibling checkout `/Users/stephen/github.com/digirati-co-uk/tasks-api/src/routes/delete-task.ts` deletes rows with `root_task`, `parent_task`, or **`delegated_task` equal to the deleted ID**, then the task. Deleting a contribution does not follow its outgoing `delegated_task` to delete its review. Deleting a review can remove multiple contributions delegated to it. `src/gateway/tasks/crowdsourcing-task.ts::status.2` deliberately shares an existing review between contributions; its `events` contain status events, not a model-cleanup handler for `deleted`.

The sibling checkout is supporting contract evidence, not proof of the running `ghcr.io/digirati-co-uk/tasks-api:latest` image. Confirm actual behaviour during parent runtime checks. Do not implement “delete a review and assume that deletes only this contribution.”

## Recommended bounded implementation

1. Harden and explain the existing canvas operation in `src/routes/projects/delete-project-capture-model.ts`: validate the model's site/project/template/Canvas target before any destructive call; collect the deletion set first; preserve the existing project/root/subject boundary; propagate non-404 failures. Retain a documented 204 response for successful deletion. A retry must be able to finish task cleanup when the model has already disappeared; do not rely solely on reloading a now-deleted model to rediscover its target. If that retry guarantee needs a different request contract, plan it explicitly rather than pretending the present model-ID-only API is transactional.
2. In `src/frontend/site/features/canvas/CanvasTaskProgress.tsx`, show pending/error/success feedback and refetch the model **and** canvas/manifest task data using the active query provider. Confirm the visible dialog accurately describes the deletion scope. In `src/frontend/site/pages/tasks/actions/reject-submission.tsx`, correct the retained-revision wording. In `src/frontend/site/features/manifest/ManifestTaskProgress.tsx`, describe the existing action as task reset until runtime proves model deletion; do not market it as permanent contribution erasure.
3. Individual deletion is feasible for an uncomplicated **unapproved, unmerged, exclusively referenced revision** by orchestrating existing APIs. Proposed new admin-only route `src/routes/projects/delete-project-contribution.ts`, registration in `src/router.ts`, and `deleteProjectContribution(projectId, taskId)` in `src/gateway/api.ts`; no migration and no new status. Resolve task→project root→model→revision server-side. Check type `crowdsourcing-task`, subject, site, model derivation, revision ID, no accepted/merged/canonical dependency, and no other contribution referencing the revision before deleting anything. Delete that revision and its one contribution task; delete a linked review only after proving no remaining contributions or active merge depend on it. Otherwise preserve the review. Existing parent/sibling task reads and task list filters can establish this in ordinary one-resource cases; it is not a raw button calling two unrelated deletes.
4. Expose that one action in `src/frontend/site/pages/tasks/review-listing/single-review.tsx` and, if the parent includes the ordinary task detail surface, a small shared `src/frontend/site/features/tasks/DeleteContribution.tsx`. Use a confirmation naming contributor/resource and explain removal scope. Permit no structural/root/whole-review deletion here. Keep unsupported merged/approved cases read-only with a link to the correction flow from [NS-49](NS-49.md). A design can be concrete now; enabling it requires the ownership/failure checks above.

For stages 1 and 3, add focused route regression tests under `__tests__/routes/projects/` using small API stubs, not a heavily mocked database suite. Stage 2 needs manual interaction checks, not presentational snapshot tests. Updated styled-components files must be migrated to Tailwind under AGENTS.md; use small focused components.

## Acceptance tests and parent runtime checks

* Bulk delete in project A with two contributors removes A's target model/revisions and intended user tasks. Project B using the same Canvas, adjacent canvases, and unrelated reviews survive. Verify both canvas and manifest claim configurations.
* Check task and review listings after deletion, reload, and client navigation. Record any orphan review; the current contribution-only loop cannot be assumed to remove it. Cached contributor totals must refresh immediately.
* Invalid project/model association fails **before** model deletion. Missing model/task, partial task-service failure, unauthorized access, and retry produce truthful outcomes rather than false success.
* For individual deletion: two contributions sharing a review; two tasks sharing a revision; merged and accepted revisions; an active merge; a structural task ID. Only the exclusive unapproved case is eligible, and a failed write must not close the dialog as success.
* Inspect model reads, published annotations, exports, Typesense results, and contribution analytics after deletion. Raw delete methods do not run the approval worker's indexing path. Parent should rebuild/restart server for backend changes and smoke-test authenticated `https://madoc.local`; this research task did neither.

## Risks and decisions deferred

Task service and model storage have no shared transaction. Mutation order, retries, concurrent submission, and shared-review references must be explicit. Do not silently reopen completed structural parents or replay approval/rejection notifications as cleanup. Approved/merged contribution deletion, attribution removal from canonical values, publication/feed withdrawal, and automatic parent-status recalculation need a separate lifecycle decision. Admin correction of approved values is the useful bounded alternative; see [NS-49](NS-49.md) and [NS-79](NS-79.md). A generic “delete any task and its contributions” action is outside this modest change.
