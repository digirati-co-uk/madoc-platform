# NS-79 — resource capture-model review and edit

Research and implementation plan only, 2026-10-22. Ticket: <https://digirati.atlassian.net/browse/NS-79>. Paths below are relative to `services/madoc-ts`. This is a staged plan, not a source change or a claim that the new page already exists.

## Current state and evidence

The snapshot splits this request from NS-58 (“Assign Manifest page locked”), which is marked done. That does not imply that full post-submission model editing exists. The current code has useful pieces but no dedicated resource-value admin editor reachable from project task detail:

* `src/frontend/admin/pages/crowdsourcing/projects/project-tasks.tsx` delegates individual tasks to `ViewCrowdsourcingTask.tsx`, which loads the model and displays JSON. The admin `/projects/:id/model` route edits the **project template**, not the capture model of a submitted resource.
* Generic admin `/capture-models/:id/document` and `/structure` routes exist (`src/frontend/admin/routes.tsx`, `pages/crowdsourcing/capture-models/view-capture-model.tsx`). Their `FullDocumentEditor` edits field definitions, removes fields, and updates model structure. This is an authoring tool, not a safe reviewer correction surface; do not simply expose it as “edit contribution”. Its preview component also consumes `ProjectModelEditor` data, so generic preview reuse is not established.
* Site review `single-review.tsx`, `preview-crowdsourcing-task.tsx`, and `preview-manifest-crowdsourcing-task.tsx` already use `RevisionProviderWithFeatures`, selectable revisions/structures, existing field editors, and `DirectEditButton`. Completed work is restricted in the review controls; see [NS-49](NS-49.md). `review-listing/ManifestReviewViewer.tsx` already supports selecting a canvas/image for manifest-level capture, preserving `CustomRouteContext`.
* `crowdsourcing.getCaptureModel(id)` exposes all revisions for `models.create` (`src/capture-model-server/routes/capture-model.ts`). `updateCaptureModel` PUT (`routes/update-capture-model.ts`, `capture-model-repository.ts`) writes document/structure and supplied revision metadata transactionally, requiring `models.create`. No new model table or migration is needed.
* The existing structure projection is specifically **canonical plus accepted** data: `src/frontend/shared/capture-models/helpers/create-revision-request.ts::createRevisionRequestFromStructure` filters out unapproved revision fields. `capture-model-to-revision-list.ts` also creates individual revision views. “Full model” must therefore distinguish the assembled published values from an individual submitted/draft revision; selecting a structure does not automatically show every draft.

## Recommended bounded design and stages

Provide a small resource correction page using existing editor/save APIs. A model-list JSON/schema editor is not necessary, and this work should not be wholly deferred as a new review system.

1. First implement the shared permission/save behaviour in [NS-49](NS-49.md). Use `models.create` as the backend capability and a deliberately admin-only entry point. Display original author/revision status, and keep task/review outcomes unchanged. The page edits values/selectors, not field definitions, structure, target, authors, approval, or task assignment.
2. Proposed admin route `/projects/:id/tasks/:taskId/model`, registered in `src/frontend/admin/routes.tsx`, with new `src/frontend/admin/pages/crowdsourcing/projects/project-resource-model.tsx`. Load project and task, verify `root_task === project.task_id`, resolve the task's real capture-model parameter and resource target, and verify model derivation matches the project template before enabling edits. A structural task without a model should link to its concrete contribution/resource model, not guess a template ID or auto-create an empty model. A later explicit resource-ID route can broaden structural entry points once model selection is defined.
3. The new page provides “Published model” (existing canonical+accepted structure projection) and an author/status-labelled revision selector for submitted/accepted revisions. Render all declared structures/choices through `EditorSlots.TopLevelEditor` and `BackToChoicesButton`; use `revisionEditMode:false`, `directEdit:true`, autosave off, and explicit Save/Cancel. Show drafts only when deliberately selected with clear status. Never canonicalize a draft by saving the published projection.
4. Reuse `DirectEditButton`/shared correction save helper for published/canonical values, preserving revision metadata and unrelated document values. Individual revision-owned edits may use existing `updateCaptureModelRevision` after representative sparse/inherited-field tests; it cannot yet be assumed to update canonical values (the extraction layer hardcodes canonical changes off). Do not replace the full model with a filtered published document. Merge the selected projection into a freshly loaded complete model using the existing merge semantics and make value-only scope explicit.
5. Use `CustomRouteContext` with the loaded project/manifest/canvas target and existing viewers: a canvas viewer for Canvas models and `ManifestReviewViewer` for Manifest models. Use the template's existing custom renderer where compatible, including the tabular editor, rather than reducing table data to generic text fields. Extract a small shared correction editor instead of copying the large review screen and its lifecycle controls. Proposed shared home: `src/frontend/shared/capture-models/new/components/ResourceCorrectionEditor.tsx`.
6. Add a contextual link from `src/frontend/admin/molecules/ViewCrowdsourcingTask.tsx` and optionally the site single-review View options, using existing scoped link builders. Keep project-template editing separate in labels. No new backend endpoint is required for the basic page because existing model/task reads and whole-model PUT suffice; these existing permissions still govern direct URL/API access. Do not show edit mode to limited reviewers whose scopes cannot save it.

Initial source surface: new admin page, new small shared editor/save helper, admin route registration, `ViewCrowdsourcingTask.tsx`, and shared `DirectEditButton.tsx` only where success/error/refetch handling requires it. Add a new test beside the shared editor's data/save helper. Legacy files changed in implementation must follow the Tailwind migration rule. Coordinate overlap in `single-review.tsx` and `DirectEditButton.tsx` with NS-49, implementing one shared feature rather than two independent versions.

## Acceptance tests and validation

* Pure tests for task/model/project resolution and save payload construction: wrong project/root/model derivation, missing target/revision, incomplete model data, original author/status preservation, and no accidental template edits.
* Model fixtures with multiple accepted revisions and canonical values: edit one value/selector, save, reread, and ensure other revisions, sparse properties, IDs, row order and revision metadata survive. Include new/removed instances as **ineligible** in the initial value-correction scope because merge semantics can remove their revision association.
* Verify full declared structure/choice navigation and published-versus-submitted distinction, not just the first field. Editing one selected submitted revision must not publish it or affect another contributor's draft.
* Parent runtime checks on `https://madoc.local`: direct SSR load, client navigation, admin/limited-reviewer/contributor access, actual resource image selection, Canvas and Manifest models, tabular/custom renderer, completed resource, failed save, cancel/navigation with unsaved values, and return to the originating task.
* Confirm task statuses, reviewer assignment, completion counts, notifications, feed entries and authors are unchanged by correction. Check published read/export and Typesense refresh: whole-model PUT does not emit approval task events. Use an existing targeted indexing call if needed and authorized; never trigger an approval transition for indexing.
* Parent owns builds and runtime checks; this documentation task ran no pnpm commands, Docker actions, or mutations.

## Risks, decisions, and deferred scope

Whole-model PUT can overwrite concurrent edits and `mergeDocument` mutates its input. Fresh load plus a copy prevents accidental cache mutation but does not provide optimistic locking. Save error and stale-editor behaviour must be explicit. Revisions/canonical values can share fields, so warn the admin when correcting a canonical value visible in several views; do not imply the save is private to one author's task.

Whole-model upsert does not update existing revision `revision_data`, so tabular alignment changes are not covered by simply reusing that save button. Preserve alignment and restrict this increment to existing cell values/selectors; any alignment controls need the narrower revision API and dedicated checks, as described in NS-49.

The bounded feature covers a resource's assembled accepted content and selected existing revisions. Arbitrary field/schema redesign, multi-resource bulk editing, merging/deleting annotations, reassigning/reopening approved contributions, editing all drafts as one published document, and a new revision audit/versioning system remain separate work. Neither NS-58's historical done status nor the generic model authoring routes justify silently introducing those policies.
