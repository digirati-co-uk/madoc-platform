# NS-73 — CSV export per manifest

## Assessment before implementation

The current code supports a bounded addition without migrations. `src/extensions/project-export/export-configs/project/project-cvs-contributions-export.ts` already exports individual field contributions (including revisions), original target URIs and tabular review metadata. `project-csv-simple-export.ts` instead groups by document and selects unrevised field values. These are different existing contracts; neither should be replaced based on historical ticket comments.

Paths below are relative to `services/madoc-ts`. `src/gateway/tasks/export-resource-task.ts` already fans project exports out into manifest children, writes child files to a shared temporary directory, and produces a ZIP. However, it only subscribes to successful children, so a failed manifest can prevent a downloadable final archive. `src/routes/projects/get-project-raw-data.ts` and `CaptureModelRepository.queries.modelFieldRevisions` currently fetch an entire project's fields; filtering only in the exporter would repeat that expensive query for each manifest.

## Implementation plan and acceptance

1. Add an optional validated manifest ID to the existing raw-field API, `src/gateway/api.ts`, and `src/capture-model-server/capture-model-repository.ts`. Filter `capture_model.target` before expanding document fields; retain the project/site restriction. Test query scoping and rejected invalid IDs.
2. Reuse the contributions CSV renderer through a small scoped helper and register a new manifest CSV definition in `src/extensions/project-export/extension.ts`. Give each manifest/project pair its own file. Preserve the project CSV path and every contribution/revision row. Test row count, target IDs, configured field ordering, filters and distinct paths.
3. Extend the existing export-task terminal event handling for the new manifest CSV plan so all siblings run and a partial ZIP can finish after failures. Keep failed children failed and record the partial result. Verify fan-out, completion gating, errors and API disposal on success/failure. Do not edit the project task UI.
4. Make the new option configurable from manifest admin as the narrow NS-78 integration, with one explicit project selection at a time.

## Risks and boundaries

No database migration, new task type, new orchestration service, merged whole-project CSV, or replacement of either project CSV format is planned. Work still scales with the size of an individual manifest. Existing task retries and archive cleanup need runtime verification; a completed partial archive should be downloaded before starting a fresh export to recover failed manifests. API and SQL changes require server and producer builds by the parent. Authentication and project membership remain governed by the existing admin/raw-field API.

## Validation

Run focused Jest tests with Node 24. Parent runtime checks: export a project containing at least two manifests, verify one CSV per manifest with no cross-manifest rows, compare a representative CSV with the existing contributions format, force one child failure and confirm successful siblings are in the partial ZIP and the failed task retains its error. Check empty output and a manifest with multiple contributions/revisions. Confirm existing project CSV exports remain available.

## Implemented scope and verification

The new definition is `src/extensions/project-export/export-configs/manifest/manifest-csv-contributions-export.ts`, registered in `src/extensions/project-export/extension.ts`. It uses the shared renderer extracted from `src/extensions/project-export/export-configs/project/project-cvs-contributions-export.ts` and writes `/manifests/{manifest}/csv/{project}/contributions.csv`. The raw-field query/filter changes are in `src/capture-model-server/capture-model-repository.ts`, `src/routes/projects/get-project-raw-data.ts` and `src/gateway/api.ts`. Both old project CSV definitions retain their existing semantics and paths.

`src/gateway/tasks/export-resource-task.ts` now subscribes CSV tasks to their own `status.3` and `status.-1` events and reconciles the direct parent on either terminal event. This matters because the external task API's `src/utility/dispatch-update-subtask-status.ts` emits `subtask_type_status` only when every sibling of a type has the same status; mixed success/failure never emits that aggregate event. Expected child counts and output paths still gate completion. Parents write their files before queuing children; failed children remain failed; successful files are packaged with `README-errors.txt` for a partial export. CSV HTTP 404 errors remain visible to the generic worker's failure listener.

Archive publication for CSV plans is implemented in `src/extensions/project-export/publish-csv-archive.ts`: generate a complete uniquely named candidate alongside the destination, then publish through an exclusive filesystem hard link. A competing handler cannot replace the destination. Only the publishing handler updates empty-output state, removes input files and sends the notification. Replays after input cleanup reuse the published archive. Input-read errors caused by a competing publisher's cleanup do not invalidate its complete archive. Candidate files are removed on ordinary errors. Existing non-CSV export plans retain their previous behavior.

## Review corrections and verification

The earlier tests incorrectly invoked an aggregate failure event for mixed siblings and checked only sequential completion. Regression coverage now uses the verified task API dispatch contract (own-status event on every status PATCH, aggregate event only for unanimous sibling statuses), exercises both mixed completion orders, and runs overlapping real handlers against the filesystem. The overlap test forces both handlers to read an old parent and PATCH 3, then waits until both complete candidates exist before releasing their atomic publication attempts. It verifies CSV bytes, partial-error notes, one notification, and a byte-identical archive after replay with deleted input files. Publication failure also verifies that no incomplete ZIP or candidate remains visible and source CSVs can be retried.

Node 24 validation passed **34 tests across seven suites**; scoped diff whitespace checks also passed. The focused suite set comprises `__tests__/gateway/tasks/export-resource-task.test.ts`, `__tests__/extensions/project-export/{manifest-csv-contributions-export,browser-csv-export,project-csv-simple-export,export-cache-lifetime}.test.ts`, `__tests__/routes/project-raw-data.test.ts`, and `__tests__/frontend/admin/manifest-export.test.tsx`. Use Node 24 and `pnpm test --runInBand` with these paths. The dispatch harness models the verified external contract; it is not a database-backed integration test of the external service.

Parent runtime checks: rebuild the server/producer and frontend bundles as appropriate, then submit a fresh two-manifest export and force either the first or last child to fail. Download the partial ZIP, inspect successful CSVs and `README-errors.txt`, and confirm the failed child retains its error. Replay duplicate completion events and verify the archive bytes remain unchanged. Fresh tasks are required: older persisted tasks do not acquire the newly added failure-event subscription.

The storage directory must support hard links (candidate and destination are on the same filesystem); failure is surfaced and source files remain intact. The existing pipeline still buffers each ZIP in memory. Publication is idempotent, but notification delivery and cleanup are not transactional with publication: a process crash immediately after publishing can leave an unreferenced candidate or input files and miss the notification. No scheduler or automatic crash-recovery system was added. Recovery of failed manifests remains a fresh export.
