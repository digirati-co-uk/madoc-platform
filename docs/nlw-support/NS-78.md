# NS-78 — Manifest admin export feasibility

## Assessment before implementation

Feasible incrementally; exposing every project export at manifest scope is unsafe. Paths below are relative to `services/madoc-ts`. `src/frontend/admin/pages/content/manifests/manifest-export.tsx` already lists manifest/canvas export definitions and previews files through their existing APIs. Canvas model export already has a project selector. Project definitions, including both CSV formats and project API export, accept a project subject and assume project-wide data, so adding them directly to this list would export the wrong scope.

The manifest page currently resolves its configuration editor only through `useExportResources(...subjectsType: 'canvas')`. Consequently a manifest-only definition cannot get its configuration editor. The preview hook already returns the selected manifest definition: using that definition is a small integration fix.

## Small implementation plan

Expose the new NS-73 manifest contributions CSV definition through the existing registry and manifest preview. Resolve the selected manifest definition in `manifest-export.tsx`, supply the correct subject to configuration hooks, reset configuration on format selection, and let the user select one project using the existing manifest project autocomplete endpoint. Render/download the manifest-scoped CSV through `FilePreview`. This needs no new endpoint for task creation and no project task UI changes.

Acceptance: initial SSR and client navigation both show the option; select a project, optionally choose an entity/include reviews, update configuration, and download only this manifest's rows. Changing project or format must not silently reuse the previous format's configuration. Existing manifest API and canvas model previews must continue to work.

## Remaining stages and decisions

1. Confirm which formats actually need manifest-level variants. Keep project API metadata at project scope. Add simple CSV as a separate variant only if document-per-row output is wanted in addition to contribution-per-row output.
2. Decide the meaning of “all/any/selective projects”: separate files per project is recommended because capture-model schemas and field order differ. The small integration uses one selected project per download; selecting multiple projects and an all-projects default are deferred.
3. For bulk downloads, define a manifest-root export request with validated project membership, reuse existing export tasks, and add a ZIP action to manifest admin. Decide partial-success reporting and retry behavior before adding it. Do not force multi-project exports into synchronous previews.
4. Add route/permission and fan-out regression tests for that later bulk flow, then runtime-test a manifest shared by multiple projects with different models and review states.

## Risks and validation

Preview exports execute in the browser through the existing authenticated API, so a very large manifest may warrant the later asynchronous ZIP flow. No migrations or general new orchestration infrastructure are required. NS-73 tests cover CSV rows, scoping, field ordering and target IDs; parent should verify the manifest admin editor, preview/download, project switching and existing formats in the live application. This assessment does not promise every existing project export or a multi-project download in this small change.

## Implemented scope

`src/frontend/admin/pages/content/manifests/manifest-export.tsx` now resolves manifest definitions for their configuration editors, passes the correct subject to the configuration hook, recalculates the editor after saved configuration changes, and resets configuration when switching export types. The registered NS-73 definition provides a project selector scoped to the current manifest and, after choosing a project, its entity filter. CSV generation/download continues through the existing preview and `FilePreview` flow. No project tasks UI, bulk-download route, multi-project selection, or additional format variants were changed. `resetManifestCsvProjectConfiguration` clears the entity filter when the selected project changes or is cleared, preserving review selection; a project-keyed editor remount prevents the prior model's editor state from persisting. A component regression test drives the actual manifest page's selection/save handlers and checks the configuration passed to preview and the new entity autocomplete source.

The previously missing CSV preview was caused by `ExportFile.csv` dynamically importing the default Node stream entry of `csv-stringify`; the browser threw `ReferenceError: Buffer is not defined` after the raw-data/target reads succeeded. The installed 6.8.3 package explicitly exports `csv-stringify/browser/esm/sync`. `src/extensions/project-export/server-export.ts` now uses that entry in the browser while retaining the existing callback-based server entry. The browser regression executes the installed browser bundle without Node globals and compares its quoting/Unicode/multiline output with the server implementation. A real browser dynamic import from the hot-reloaded dev server successfully returned CSV while `typeof Buffer` was `undefined`.
