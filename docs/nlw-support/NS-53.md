# NS-53 — project crowdsourcing overview

Implemented in the shared checkout, 2026-10-22. Ticket: <https://digirati.atlassian.net/browse/NS-53>. Source paths below are relative to `services/madoc-ts`. Parent owns builds and runtime checks.

## Current state and delivered scope

`src/frontend/admin/pages/crowdsourcing/projects/project-tasks.tsx` now renders a paginated immediate-child overview for project/collection/manifest task lists. It preserves the existing canvas/contribution detail branches, their complete subtask lists, the “Go to reviews” link, and manual reviewer assignment. It does not flatten nested projects.

`project-task-query.ts` normalizes URL-backed page/status/sort settings and includes all effective values plus project/task IDs in the universal loader key. `loadProjectTaskOverview` reads the project context and parent, then calls `getTasks(page, { parent_task_id, root_task_id, detail:true, per_page:20, status, sort_by })`. Parent/root scope comes from loaded data. Overview requests never use `all:true`; complete detail views and the deliberate reviewer-assignment operation retain it. The parent response's embedded children are ignored for the overview. The list response uses camelCase pagination (`page`, `totalResults`, `totalPages`).

`project-task-overview.tsx` provides a Tailwind table with resource label/thumbnail, cached manifest canvas count, actual task status text, and task update date. Status chips and sort headers use links; filter/sort changes reset page to one. Pagination preserves filters. Row drilldown also starts the child list on page one while retaining status and sort, so entering a short child list from parent page three cannot strand navigation on an empty page. Previous pages remain visible while loading, but previous resource/detail views are not retained across task/project navigation. Errors render a load-error callout. Empty results are distinct from failures.

Cached snippets are rendered directly. There are no per-row metadata hooks or model/manifest/revision/user requests. A count of zero stays zero; missing metadata/counts display “—”. No latest-contributor, annotation-count or contribution-activity claim is made. The footnote states the limits of cached counts and task dates. Actual `status_text` is preserved: structural status 2 can mean `max contributors`, rather than a universal review stage.

## Verified API evidence

The parent verified the running API returns numeric millisecond `modified_at`, accepts `sort_by=modified_at:desc`, and respects `per_page`, one-based `page`, and status filters. Project 1 root task `8fd23daa-ef90-4e99-8eab-0549e9198602` has two manifest children with empty metadata; their canvas counts remain unknown.

`src/gateway/api.ts::getTasks` already supports the needed list filters. Sibling tasks-api source (`src/routes/get-all-tasks.ts`, `src/utility/parse-sort.ts`) supports explicit `field:asc|desc`, limits pages to 50, and distinguishes immediate-child `parent_task_id` from descendant `root_task_id`. The legacy `newest` alias is avoided. No ApiClient edit was necessary.

Cached `metadata.subject.itemsTotal` is populated by `src/extensions/tasks/resolvers/subject-resolver.ts`. Resolving absent row metadata through `useTaskMetadata` would create N+1 requests, so this implementation deliberately displays unknown values.

## Deferred aggregate work

Latest contributor, annotation totals and a true latest-child timestamp need a batched read contract with agreed counting rules and rejected/merged inclusion. Task assignees are not authoritative latest contributors; contribution counts are not annotation counts. Do not replace that work with loading every project task in the browser or one query/model load per row. No backend endpoint, database migration, completion-policy change, global ApiClient edit or translation edit is included.
