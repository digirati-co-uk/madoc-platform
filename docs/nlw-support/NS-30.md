# NS-30 — Date, time and numeric capture inputs

## Current state and evidence

The ticket snapshot is `/tmp/madoc-nlw-NS-30.json`. The current code already registers `date-field` in `src/frontend/shared/capture-models/editor/bundle.ts`. `DateField` stores strings and uses `utility/date-field-format.ts` for DD-MM-YYYY entry and calendar validation (including three-digit historical years). `TextField` stores arbitrary strings and has no numeric/time format option. The tabular editor has its own date formatting, so changing the date representation globally would risk existing contributions.

## Implementation plan

1. Keep the existing date-only registration, configuration and DD-MM-YYYY behavior intact.
2. Extend the existing registered `text-field` with an optional `inputFormat` setting for Number, Time and Date and time. Use text input and non-destructive format guidance/validation; do not coerce strings into JS numbers or Dates, change timezones, strip zeros, or sanitize saved legacy text.
3. Add small format helpers under `src/frontend/shared/utility/` and an existing-style Formik select to `TextField.editor.tsx`. Migrate the touched TextField and editor components from styled form controls to Tailwind, preserving multiline autosizing and preview options. Multiline fields retain their existing unrestricted behavior.
4. Test valid/invalid/empty numeric and time strings, date-time calendar boundaries, legacy default behavior and exact value preservation.

## Acceptance tests

Date-only fields continue displaying/entering DD-MM-YYYY. New and existing text fields can opt into Number (signed decimal, optional exponent), Time (24-hour HH:mm, optional seconds/fraction), or Date and time (DD-MM-YYYY followed by that time). The control explains the chosen format and marks mismatches. Old configurations behave as plain text; saved text is displayed verbatim, including legacy mismatches, leading zeros, decimal precision and partial input. Updates remain string values.

## Risks, deferred stages and decisions

No database, export, query or revision representation changes. These formats provide entry guidance, matching the existing date field's advisory validity behavior. Hard submission enforcement is deferred: it needs a separately agreed policy for incomplete/historical/uncertain values and legacy contributions, and coordinated validation in every editor and server path. Arbitrary regular expressions and masks are deferred for the same reason. Native date/time/number inputs would hide or sanitize incompatible stored strings, so use text controls. The tabular project's separate editor does not consume these text-format settings; adding those controls and validating them in tabular imports/exports is a separate follow-up. Existing date-field formatting remains unchanged rather than broadening this task into that editor.

## Validation and integration handoff

Run focused format and compatibility tests on Node 24 and targeted static checks. Parent performs builds and browser checks in the generic model editor: create each format, save/reopen, enter partial/invalid/valid text, clear, exercise multiline autosizing, and reopen a legacy contribution. Verify existing date-only tabular behavior and export strings remain unchanged. No Docker restarts or commits in this task.

## Implementation result

Implemented optional `inputFormat` guidance in the existing text-field registration; the date-only field is unchanged. Owned source files are `services/madoc-ts/src/frontend/shared/utility/text-field-format.ts` and `TextField.tsx`, `TextField.editor.tsx`, and `index.ts` under `services/madoc-ts/src/frontend/shared/capture-models/editor/input-types/TextField/`. The touched controls now use Tailwind and retain the existing `react-textarea-autosize` behavior for multiline input.

`__tests__/frontend/shared/utility/text-field-format.test.ts` covers numeric, time and date-time formats and the established date-only behavior. `__tests__/capture-models/editor/text-field-formats.test.tsx` verifies stored strings (including invalid legacy data and high-precision numbers) remain visible verbatim and multiline input remains unrestricted. All 51 tests across these two suites and the NS-10 suite passed on Node v24.21.0; targeted ESLint passed. Repository-wide TypeScript validation is blocked by installed dependency declaration syntax that TypeScript 4.9 cannot parse (see the NS-10 validation result). Browser checks and builds remain with the parent. Mandatory validation, regex masks and the separate tabular editor remain deferred rather than claimed as delivered.
